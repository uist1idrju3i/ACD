# 知識ベース

**ステータス：Draft**

## 目的と権威範囲

READMEの「3. 知識の蓄積」と「知識は蓄積される」を、再利用可能で説明可能なオブジェクトとして定義します。READMEのPhase 0が要求するデータモデルの一部として、`KnowledgeItem`は[`../schemas/design-graph.schema.json`](../schemas/design-graph.schema.json)に表現します。知識はモデルの暗黙記憶ではなく、出所付きでレビュー可能な`KnowledgeItem`です。

## オブジェクトモデル

知識オブジェクトは、少なくとも次を持ちます。

- `id`、版、状態（候補・レビュー済み・採用・廃止）
- **source event**：fab指摘、測定、承認・却下、部品変更、検証結果
- **provenance**：元の設計リビジョン、証拠ID、ツール、時刻、作成者
- **scope**：`project-local`（一案件のみ）または`library-wide`（同一ユーザーの複数案件で再利用可能）
- 適用条件、除外条件、信頼度、既知のリスク
- 変更した判断と、説明に使う過去イベントID

設計データ、顧客固有情報、秘密の回路と、一般化した手順・fabルールを分離します。プロジェクト固有の知識を、同意なくlibrary-wideへ昇格させません。

現時点の`library-wide`は、同一ユーザーが複数プロジェクトで再利用するユーザー個人のライブラリを意味します。組織、テナント、fab／プロセス共有、コミュニティへの展開は現在のスコープ外であり、将来作業とします。

## 「標準、そして改善」

検証済みの手順をバージョン管理された現時点の標準として保存します。次の設計は標準を最初の候補として使い、例外は明示します。測定やfabフィードバックで標準が不十分だと分かったら、小さな変更としてレビューし、次の版へ書き戻します。標準があるから逸脱が見え、逸脱を根拠に改善できます。

製造プロファイルごとに、重要特性、確認方法、頻度、判定条件、異常時の反応計画を版管理した**Control Plan相当**として保存できます。PFMEA相当のリスクや過去の不良から項目を更新し、変更・材料・サイト・供給元の差分では影響分析から再確認すべき項目を選びます。

## QC七つ道具と新QC七つ道具の生成分析

詳細な手法契約と入出力表は[`qc-tools.md`](qc-tools.md)を参照します。

ACDは、正規設計グラフとイベントログから、数量データ向けのQC七つ道具（Q7）と、言語・計画データ向けの新QC七つ道具（N7）を別体系として生成します。Q7はパレート図でDFM／fab指摘の標準化優先度を付け、ヒストグラム・散布図・管理図で測定値、ゲートメトリクス、ゴールデンタスクの分布・関係・時系列ドリフトを見ます。チェックシートはTestItem、停止理由、実装不良の収集形式とし、特性要因図はRationale・Evidence・工程リンクから故障原因候補を整理します。分類によってはQ7の七番目を層別、グラフ、フローチャート、ランチャートのいずれかとして扱うため、生成物の定義を明記します。

N7は、親和図でStep 1の要求・自由記述をクラスタリングし、連関図で相互原因、系統図で要求→機能→部品→試験を分解し、マトリックス図で要求×テストや変更点×影響先を示します。マトリックス・データ解析はN7内の数量手法として候補部品・材料の多変量比較に使い、PDPCはタスク失敗・在庫消失・fab差戻しの分岐計画、アローダイアグラムはTaskLedgerの依存関係とクリティカルパスに使います。図表は対象revision、イベント範囲、入力ハッシュ、Evidenceを参照する派生投影であり、Q7/N7の異常やドリフトはjidoka停止とKnowledgeItemへの標準化候補になります。

## fabフィードバックからフットプリント修正へ

1. fab報告を対象ジョブ、設計リビジョン、部品、座標、ルールへリンクする。
2. 人間の文章を構造化した問題、重大度、再現条件へ変換する。
3. フットプリントまたはfabプロファイルへのパッチ候補を作る。
4. ゴールデンタスクと再オープン、DRC/DFMで候補を検証する。
5. プロジェクト内で採用し、一般化できる場合だけlibrary-wide候補にする。

## 不具合と是正のクローズドループ

停止、ゲート不合格、fab指摘、実機故障、および実害には至らなかったが停止条件に近い事象を同じ台帳へ記録し、症状→原因→是正→有効性確認→水平展開の順に閉じます。有効性確認は再現条件でのゲート再実行または実測`Evidence`で行い、説明だけで閉じません。水平展開では、同じ原因が影響し得る他プロジェクト、fixture、ライブラリ、fabプロファイル、ゲート規則を列挙し、対象外にしたものは理由を残します。是正が未完了の項目は次の設計の入力として残します。

## KnowledgeItemのライフサイクル

状態は`candidate`→`reviewed`→`adopted`→`deprecated`とします（Schemaの`KnowledgeItem.status`）。昇格には出所、再現条件、適用条件と除外条件が必要です。適用条件（fab、材料、部品、版、期間）を外れる再利用は禁止します。誤りが判明した知識は`deprecated`にし、その知識を根拠に行った判断と`VerificationResult`を洗い出して再検証対象にします。内容を黙って書き換えません。却下した案、失敗したspike、再現しなかった結果も条件付きで残し、同じ検討の反復を防ぎます。

## 説明可能性

知識が部品、配置、ルール、テスト項目の判断を変えたとき、UIは「どの過去イベントが、どの知識版を経由し、どの判断を変えたか」を表示します。説明できない書き換えは採用せず、未確認の推測は`uncertainty`として残します。
